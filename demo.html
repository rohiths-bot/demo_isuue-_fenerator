A2Approach — why Playwright, and where the AI agent fits

  • Style: robotic end-to-end UI driving (Selenium-like), but with modern tooling.
  • Framework: Playwright v1.61 (already installed), driven live by a Claude agent via the Playwright MCP server — the agent reads each page snapshot, performs the flow, asserts the result, and emits a repeatable .spec.js per green flow.
  • Why Playwright over Selenium: the saves are AJAX (POST …/savesalesdetails etc.). Playwright auto-waits on both element state and network, avoiding the manual sleeps that make Selenium flaky on this jQuery/Smarty app. No end-of-life Python dependency.
  • Two execution modes: (a) live agent run (/ui-smoke) for authoring and selector-drift repair; (b) headless regression via npx playwright test — the mode the migration uses daily.

★The plan in one minute — plain words

Read only this table if you have 60 seconds. Everything below is the detail behind each answer.

QuestionAnswer
What is the problem? TRAACS runs on PHP 7.4 — the "engine" under the application. It has had no security fixes since Nov 2022. Like running Windows XP: it works today, but it is risky for a finance system and gets harder to support every year.
What do we want to do? Upgrade only the engine to PHP 8.4. Screens, features, workflows and the database stay exactly the same — users should notice nothing.
Do we rewrite the application? No. A rewrite of 3.9 million lines would take years and cost millions. We keep the current framework by swapping in a maintained modern copy that uses the same names — the application code barely changes.
Where does the work actually go? Two things. (1) Replacing a few very old bundled components — mainly the screen-display engine (used by every screen) and the Excel-export library (used by 559 files). (2) Hand-checking ~900 lines of money-comparison code that PHP 8 treats differently.
How long, and with whom? About 6 months with 3 developers + AI tools (best case 4.5, worst case 8). Without AI it would be roughly 9–12 months.
Does normal work stop meanwhile? No. New features and fixes continue on the current system exactly as today; the migration runs on a separate copy that is kept in sync weekly. Only the final 2–3 weeks before go-live restrict releases to critical fixes.
What do we ask for today? Only a 3–4 week trial (Phase 0) by 1 developer: get the application to start on PHP 8.4. The big budget is committed only if the trial passes. If it fails, we lost weeks, not months.
What is the biggest risk? The app has almost no automated tests, and PHP 8 can silently change some money calculations. Answer: build an automated smoke-test suite early, hand-review all 889 flagged calculation lines, and run old vs new side by side before go-live.
What if we do nothing? The cost never goes down — the security exposure, the dying libraries and the shrinking developer pool only make the eventual jump bigger and riskier.

1Why upgrade at all — and why now

  • PHP 7.4 is end-of-life. Security fixes ended 28 Nov 2022. Every year on it widens our exposure window on an internet-facing finance application.
  • The ecosystem has moved. New OS images, extensions, libraries and security patches target PHP 8.x only. We are already pinning old containers to keep 7.4 alive.
  • Hiring and retention. PHP 7.4 + Smarty 2 is a shrinking skill pool; PHP 8.4 keeps the stack maintainable by the people we can actually hire.
  • Why 8.4 and not 8.1/8.2: the migration cost is nearly identical wherever we land (the breaking changes we care about arrived in 8.0), so we jump once to the version with the longest support runway instead of paying the QA bill twice.

3Key decision — keep the current framework, no rewrite

The application's framework (Zend Framework 1) looked like the scary part. It is not:

  • Our vendored Zend is stock 1.10.6 (2,218 files) with only 3 local patches — a module-path split in ViewRenderer.php:844 and 2 custom authentication adapters.
  • We swap it for shardj/zf1-future 1.25 — the community-maintained fork of ZF1, compatible up to PHP 8.4/8.5. Same Zend_* class names, so the 3,297 application files that use Zend classes do not change at all.
  • The 3 patches get re-applied outside the vendor tree, so future framework bumps stay clean.
  • Estimated effort: 3 person-weeks — versus a multi-year, multi-million full rewrite.

5"Last time we upgraded with scripts" — why 7.4 → 8.4 is different

A fair question from anyone who remembers the PHP 5.6 → 7.4 upgrade: that one was largely scripted find-and-replace. Why can't this one be? Because the two jumps break in fundamentally different ways:

5.6 → 7.4 (last time)7.4 → 8.4 (this time)
Nature of the breaks Mostly removed functions and old syntax — fixed patterns a script can find and replace one-to-one (ereg→preg_match, split→explode, old-style constructors, mysql_* wrappers). Mostly behavior changes — the same line runs on both versions but returns a different answer (== comparisons, string↔number rules, null handling) — plus two whole-library replacements (Smarty, PHPExcel) whose successors have different APIs, not different spellings.
How a missed spot shows up Loudly. A missed call crashed with a fatal error the first time it ran — easy to catch in testing. Silently. A wrong figure in a refund calculation. No crash, no log line — only a person comparing outputs notices.
Can a script decide the fix? Yes — the replacement was mechanical and always correct. Often no. A script can find every == (we did — 889 sites), but it cannot know the business intent of each one. Blindly converting them all to === would itself change behavior and break working logic.
View / export layers Smarty 2 and PHPExcel still ran fine on 7.x — untouched. Both are dead on 8.x. 2,055 templates and 559 export files must move to different-API successors — a migration with visual verification, not a substitution.

6The silent risk — PHP 8 changes how some money checks behave

PHP 8.0 changed how == compares numbers with text (e.g. 0 == "abc" was true, is now false). In tax / refund / settlement calculations this can produce wrong figures with no error message. It is the highest-judgment, least-automatable part of the work.
  • 6,669 loose comparisons live in the 10 finance controller directories; 889 compare against literals in 67 files — that is the human review surface.
  • Worst offenders: Refund/Refund.php (207), Refundnetrevenuetransaction.php (75), Refundcostofsalestransaction.php (60), Againstinvoice.php (45).
  • Refund is the highest-risk subsystem. A senior developer reviews these by hand — automated tools cannot decide the intent of a comparison. An AI-generated checklist of all 889 sites already exists.

8Business does not stop — new work during the 6 months

TRAACS ships new waves and support fixes continuously. The migration cannot freeze development for 6 months — so the plan runs two streams in parallel and controls the drift between them.

How the two streams run side by side

MechanismHow it works
Production stays on 7.4 All new waves, fixes and releases continue exactly as today, on the current branch and runtime. Customers see zero change until cutover.
Migration runs on its own branch All migration work happens on a dedicated SVN branch — it never blocks or destabilizes a business release.

Short final freeze Only the last 2–3 weeks (final regression + UAT + cutover) restrict releases to critical fixes — agreed with management in advance, not sprung on the business.

12Questions & answers

The questions we expect from management and the team — answered from the evidence.

Why not just rewrite the application in a modern framework (Laravel / Symfony)?

Scale. This is ~3.9 million lines of code, 2,815 controllers, and 2,055 screens of working, revenue-critical finance logic. Industry experience with rewrites of this size is consistently multi-year and high-failure-risk, and during the rewrite the old system still needs maintenance — double cost. The measured evidence says the framework is not the problem: swapping to the maintained zf1-future fork costs 3 person-weeks and keeps 3,297 files untouched. We spend the budget on the actual blockers (templates, Excel, finance semantics) instead of re-typing what already works.

Is it safe to bet on zf1-future — a community fork?

It is the lowest-risk option available. The fork is actively maintained, supports PHP 7.4 through 8.4/8.5 (so we can adopt it before switching PHP versions), and keeps the exact same class names. We vendor it into our tree like the current Zend copy, so even if the fork stopped tomorrow we own the code and are no worse off than today — while gaining several years of compatibility fixes. Phase 0 exists precisely to prove this bet with ~3–4 weeks of one developer's time before any real money is committed.

Why is the template engine (Smarty) the single biggest cost?

Smarty 2.6.22 (released ~2009) fatally breaks on modern PHP, and it renders every single screen — all 2,055 templates, with no alternative view layer in the codebase. Upgrading to Smarty 5 changes plugin APIs and some template syntax, so beyond the engine swap and our 2 wrapper classes, every screen must be swept and visually regression-tested. The 14 pw is mostly that verification, which is why it is phased per module (traacs → square → nucore) rather than big-bang, and scheduled last — after cheaper phases have proven the platform.

What exactly is the "silent finance risk" and why can't a tool fix it?

PHP 8.0 changed the result of loose comparisons between numbers and strings: 0 == "ABC" was true on our current PHP and is false on 8.x. Code like if ($status == 0) where $status is sometimes a string can silently take the other branch — in refund or tax math that means wrong amounts with no error logged. A tool can find every such comparison (we already generated the list: 889 sites in 67 finance files), but only a person who understands the business rule can decide whether each one should be ===, a cast, or left alone. That is why a senior developer owns this review and why Refund — the worst concentration (207 in one file) — gets the most attention.

What happens if Phase 0 fails?

We stop, having spent ~3–4 weeks of one developer instead of months of three. Failure would mean the app does not boot on 8.4 with zf1-future for some structural reason. Fallback options in that case: target an intermediate PHP version (8.1/8.2) where the fork is also proven, evaluate the alternative ZF1 forks, or — only then — re-open the rewrite/replatform discussion with hard evidence of why in-place failed. The plan is explicitly structured so this worst case is cheap.

How can we validate a finance system that has no automated tests?

Three layers. (1) A Playwright smoke-test harness is built early (Phase 0/1, plan already drafted in TEST_PLAN.md) covering the critical journeys — login, sale entry, refund, invoice print, key reports — and runs against both PHP versions. (2) A staging parallel-run: the same real-world operations executed on 7.4 and 8.4 builds, with outputs (invoices, reports, postings) diffed. (3) Business-user UAT on finance outputs before cutover. AI generates test cases quickly, but sign-off stays with people.

Can this be done with fewer than 3 developers, or faster with more?

Fewer: yes, but the timeline stretches roughly linearly on the mechanical work — 1 developer would push well past a year, and the finance review cannot be rushed. More: adding a 4th developer helps only modestly, because the long pole is regression QA and the phased Smarty verification, which are limited by tester and business-user availability, not developer count. Three devs with clear ownership (framework / libraries / templates) is the efficient shape.

What does "person-week (pw)" mean, and how do 39 pw become 6 months?

1 pw = one developer working one week. The library work totals 39.1 pw, but much of it runs in parallel across the 3 developers, and the calendar also contains the finance review, the test harness, and the regression/UAT tail that are not library work. Parallelized, the likely calendar time is ~6 months; the 4.5–8 month range covers best case (few surprises in Phase 0/1) to worst case (heavy template or Excel edge-case fallout).

Will users see downtime or changed behavior?

No functional changes are in scope — same screens, same workflows, same database (PostgreSQL 16 is untouched). Cutover is prepared on staging with a parallel-run first, so the production switch is a runtime swap with a tested rollback (the 7.4 container stays available). The user-visible goal of this project is literally "nothing changed, and it is still supported."

What is the risk of doing nothing?

PHP 7.4 has had no security fixes since November 2022. Every year adds: unpatched CVE exposure on a finance system, growing incompatibility with OS images and libraries (we already pin old containers), a shrinking pool of developers willing to work on Smarty 2-era stacks, and a bigger eventual jump (the gap only widens). The cost of migration does not go down by waiting — the risk premium goes up.

Why do it in one jump to 8.4 instead of stepping through 8.1 → 8.2 → 8.4?

The expensive breaking changes for this codebase all arrived in PHP 8.0 (comparison semantics, removed functions, library fatals). Once those are paid, 8.1→8.4 adds mostly deprecation notices. Stepping through versions would repeat the most expensive part — full manual regression of an untested finance app — at every step. One jump, one regression cycle.

How was this estimate produced — can we trust the numbers?

Not from memory or gut feel. The analysis ran against the live codebase: PRISM (our internal code-knowledge base) for subsystem understanding, direct scans for every count in this document (file counts, template counts, comparison sites), and an 11-agent AI audit that checked each bundled library's pinned version against PHP 8.4 compatibility and counted real usage sites. Notable result of doing it this way: the feared each() problem turned out to be a scan artifact (6 real files, not thousands), and 742 controller subclasses turned out to be zero effort. The estimate also carries an explicit range (4.5–8 months) rather than a single number.

What are the milestones management can track?

Each phase has a binary exit gate: month 1 — app boots on 8.4 (GO/NO-GO); ~month 2.5 — app loads with all load-time fatals cleared; ~month 3.5 — all Excel/report exports verified; ~month 5 — finance math review complete; month 5–6 — all screens render on Smarty 5, regression + UAT pass, cutover. Progress is demonstrable at each gate, and spend can be re-decided at each one — nothing is committed blind past month 1.

The 5.6 → 7.4 upgrade was mostly done with scripts — why can't this one be?

Because the breaks are of a different kind. The 5.6 → 7 changes were mostly removed functions with one-to-one replacements — a script can find every occurrence, apply the fix, and a missed spot crashes loudly on first use. The 8.x changes are mostly behavior changes: the same line of code runs on both versions but returns a different answer (loose comparisons, string↔number rules), and a wrong answer in refund math produces no crash and no log line. A script can find every such line — we did, that is the 889-site list — but it cannot know the business intent of each one, and converting them blindly would itself break working logic. On top of that, two whole libraries (Smarty 2, PHPExcel) are dead on 8.x and their successors have different APIs — that is a migration with visual verification, not a find-and-replace. The genuinely mechanical part of this jump is scripted (Rector, Phase 0–1) — it is simply the small part this time. See §5 for the full comparison.

Development cannot stop for 6 months — how do new waves and fixes ship during the migration?

They ship exactly as today. Production stays on the current 7.4 branch and release process; the migration lives on its own SVN branch. The production branch is merged into the migration branch weekly (owner: Dev A), so drift never accumulates into a big-bang merge. From Phase 0, a dual-build CI check runs every new commit against the PHP 8.4 ruleset, so new work that would break 8.4 is flagged the day it is written. Before final regression, all the §4/§6 scans are re-run to fold in anything added during the 6 months. The only constraint on the business is a 2–3 week freeze (critical fixes only) at the very end, during final regression, UAT and cutover — agreed in advance. Full mechanics in §8.

What must developers change in their day-to-day coding, starting today?

Seven cheap habits that make every new wave 8.4-safe on arrival (table in §8): use === instead of == in money and status checks; guard nulls before string functions (?? ''); declare class properties instead of inventing them on the fly; initialize variables and check array keys; write no new PHPExcel code and no Smarty-2-only template syntax; use the cache manager class instead of direct Memcache; and avoid the removed constructs (each(), create_function(), $str{0}). None of these cost extra time when writing new code — they only stop the migration backlog from growing — and the Phase 0 CI check enforces them automatically.

What do you need from management right now?

Three things. (1) Approval for Phase 0 only: ~3–4 weeks, ~1 developer, to prove the app boots on PHP 8.4 with zf1-future. (2) A commitment of business-user time for UAT in months 5–6 (finance outputs must be signed off by the people who own them). (3) Agreement on the commit gate: the big-ticket phases (Smarty, PHPExcel) are not funded until Phase 0 is green. No other spend is requested today.

P5Path to 70% buildable — the plan

The metric: the validation pipeline rebuilds real past waves using PRISM knowledge alone and diffs the result against the code that actually shipped. Baseline (22–23 Jun 2026, 564 waves): 48% fully buildable. Since that measurement, all 776 identified knowledge gaps were closed — but the benchmark has not been re-run, so the true current score is already higher. The gap analysis says where the remaining failures live: controllers = 47% of all gaps, view-JS = 21% — and most failures are systemic (one wrong pattern document fails many waves), so fixing pattern docs lifts the score in batches, not wave by wave.

PhaseWhat we doExpected effect
1 — Land & re-measure (week 1) Commit the already-fixed systemic pattern docs (model mapper / controller / menu-insert — 14 edits + 2 new dossiers pending review); exclude self-referencing dossiers from scoring so the number is honest; re-run the benchmark on a stratified ~100-wave sample. True post-gap-closure baseline — expected ~55–60% without new work
2 — Kill the two big gap classes (weeks 2–3) Controller build recipes — one per archetype (CRUD screen, report, AJAX-only, print) with exact TRAACS conventions, each verified against 10 known-good controllers. 3 — Iterate to target (weeks 3–5) Loop the existing agent pipeline: sample-run (100 waves) → gap-analyse → gap-build → audit. Each loop ≈ one day of agent time. Exit: sample ≥70% in two consecutive rounds → full 564-wave re-run for the official number. ≥70% confirmed on the full set
4 — Hold the line (ongoing) Daily watcher agents already author coverage for each new commit; add a monthly buildability spot-check (rebuild 5 random new waves) so the score can't silently decay. 70% stays 70%

Effort: almost fully agent-automated — the builder / gap-analyser / gap-builder / audit pipeline already exists; operator time ≈ 2–4 h/week for reviewing authored dossiers. Known ceiling: some waves are inherently not buildable from knowledge alone (one-off data patches, external-partner integrations) — phase 1 classifies those as out-of-scope so 70% is measured on waves PRISM can fairly be expected to build. If phase 2 lands below 65%, the next gap class (Smarty/tpl patterns) gets the same recipe treatment.

Where PRISM meets the other two plans: the PHP 8.4 migration leans on PRISM for code archaeology, the finance-comparison checklist and impact analysis (§5/§7 of the migration plan); the QA automation agent reads PRISM's UI map for selectors and success signals. PRISM is funded by neither — it is the standing engineering-productivity programme underneath both.
